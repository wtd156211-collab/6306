# 稳定匹配与分配（从 0 实现）

## 1. 范围

从零写两样东西：

- **引擎**：根目录 `main.py`，只用 Python 3.13 标准库，不加构建步骤。`python3 main.py <用例文件>` 按第 4 节格式把结果打印到 stdout；加 `--web` 时额外写出 `web/data.json`。
- **页面**：`web/index.html`，单文件原生 HTML + Canvas，不引第三方库；用 `cd web && python3 -m http.server 8000` 起服务后访问 `http://localhost:8000/`（`file://` 下 `fetch` 会被浏览器拦住）。页面上的数字只能来自 `web/data.json`，不得在页面里重算或写死。

不做的事：不做多轮协商、议价与效用，不追求「全局最优」；不处理只有一侧有意愿的对象对；不做网络请求、持久化与账号；除 `web/index.html` 外不需要其他界面；日志与调试走 stderr，stdout 只放结果。

## 2. 口径与公式

- **两侧与方向**：偏好表分 [甲]、[乙] 两侧，**甲侧主动**（提议方），乙侧只负责接受或拒绝。两侧人数可以不等：甲多则多出的甲落空，乙多则多出的乙落空，落空者不会出现在任何配对里。
- **可接受与缺项**：甲 a 与乙 b 可配对，当且仅当 a 的偏好行里写了 b、且 b 的偏好行里写了 a。只写一边＝单方意愿，直接跳过，不参与稳定性判定。偏好行整行留空＝对谁都不可接受；不完整偏好只是「只写了部分对象」，写法与完整偏好没有区别。
- **名次与并列**：名次 1 最优先，数字越小越优先；同一行里名次相同即并列。并列只说明「一样想要」，**并列不算更偏好**。
- **并列的打破（只用于算法过程）**：需要分出先后时按「名次小者优先；名次相同者按标识码点升序优先」拉成严格序，甲侧的提议顺序与乙侧的取舍都用它；稳定性核验**不得**使用它。
- **稳定（弱稳定）**：配对 M 稳定 ⇔ 不存在阻塞对 (a,b)，即不存在 (a,b) 使 acc(a,b) ∧ betterₐ(b, M(a)) ∧ better_b(a, M(b)) 同时成立：a 与 b 互相可接受，且各自未配对或更偏好对方于其配对对象。better 用**原始名次**判定（严格更小才算更偏好），未配对视同比任何可接受对象都更优。
- **核验方式**：固定结果里的配对与落空名单，枚举全部互相可接受的对象对，逐对套上面三条判断，结论必须是 0 个阻塞对。

## 3. 状态机与数据结构

- 每侧偏好读成 `{标识: [(对方标识, 名次), ...]}`，再建名次索引供常数时间比较。
- 每个甲侧 a 维护**提议游标**（走到偏好表第几个）与**当前配对**（可空）；每个乙侧 b 维护**当前接受的甲**（可空）。
- 主循环（延迟接受），每轮固定取「尚未配对且游标没走完」的甲侧中标示最小者 a：
  1. a 向游标所指的 b 提议，游标前移一格。
  2. b 还空着：暂时接受 a。
  3. b 已有对象 a′：按第 2 节的严格序比较，更偏好 a 就把 a′ 换成 a，a′ 重新变自由；否则拒绝 a，a 保持自由继续往下提议。
  4. a 的偏好表走完仍没有配对：a 永久落空。
- 每对可接受对象最多被提议一次，所以提议总数 ≤ 可接受对数 ≤ 甲人数 × 乙人数；循环用迭代实现，不要用递归。
- 主循环结束时，乙侧当前接受者即最终配对，没人接受者落空；提议次数由「每轮取标识最小的自由甲侧」定死，要写进 `stats.proposals`。

## 4. 输入输出与文件格式

### 用例文件（UTF-8 文本，允许 CRLF）

```text
# 注释行可省略
[甲]
a1: b2=1, b1=2, b3=3
a2: b3=1
a3:
[乙]
b1: a1=1, a2=2
b2: a1=1
b3: a2=1, a1=2
```

- 空行与 `#` 开头行忽略；`[甲]`、`[乙]` 各恰好一次，`[甲]` 必须在 `[乙]` 前面。
- 数据行写法 `标识: 对方=名次, 对方=名次, ...`：名次是正整数，从 1 开始且连续，同一行按名次不降序书写；名次相同即并列；同一对象一行里只能出现一次；冒号后留空表示对谁都不可接受。
- 标识由 `A-Za-z0-9_` 组成、长度 1~16、区分大小写；甲、乙两侧合起来不能重名，行里引用的对象必须在另一侧定义。
- 名次跳号或乱序、重复对象、缺段、重名、引用不存在的标识等一律算格式错误：退出码 2，stderr 给出带行号的中文提示，stdout 不输出任何结果行。

### 结果（stdout，UTF-8，LF 换行）

```text
[配对]
a1-b2
a2-b3
[落空-甲]
a3
[落空-乙]
```

三个段标题必须出现且顺序固定；配对按甲侧标识升序，落空名单各按自身标识升序；某段没有内容时标题后直接跟下一段；末尾留一个换行。比对时忽略行尾空白与文末空行，其余逐行一致。

### 页面数据（`python3 main.py --web <用例文件>` 写出 `web/data.json`）

```json
{
  "case": "04-ties.txt",
  "prefs_a": {"a1": [{"id": "b2", "rank": 1}, {"id": "b4", "rank": 1}]},
  "prefs_b": {"b1": [{"id": "a3", "rank": 1}, {"id": "a4", "rank": 1}]},
  "pairs": [{"a": "a1", "b": "b4"}],
  "unmatched_a": [],
  "unmatched_b": [],
  "stats": {"matched": 4, "proposals": 10, "blocking": 0}
}
```

键一个都不能少；`prefs_*` 给全量条目并按名次、标识升序（并列原样保留），`pairs` 按甲侧标识升序，`stats.blocking` 是引擎按第 2 节核验出的阻塞对数（正确实现恒为 0）。页面必须一眼看到：两侧偏好表（并列可辨）、Canvas 画出的配对连线（甲乙各一列）、两侧落空名单、`stats` 的三个数字。

上面的 JSON 只是节选，实际要写全每个标识的偏好条目。

## 5. 性能与验收口径

- **规模**：单侧最多 1000 人、每人最多 1000 个条目；两侧都完整时约 100 万个可接受对象对。
- **预算**：上述规模单次运行 wall clock ≤ 6 秒、峰值内存 ≤ 512 MB（单核、近五年桌面 CPU，解析时间也算）；复杂度按提议数计不高于 O(甲人数 × 乙人数)，不得反复复制或重排全量偏好。
- **验收**：
  1. 对 `samples/cases/*.txt` 逐个运行引擎，stdout 与 `samples/expected/<同名>.result.txt` 逐行一致（按第 4 节的忽略规则）；
  2. 每份结果的阻塞对数按第 2 节核验为 0，且 `stats.blocking` 与之一致；
  3. `samples/` 下的文件不得改动；非法输入必须退出码 2 且不打印结果段；
  4. `--web` 产出的 `web/data.json` 能被页面读出，页面上的配对数、提议次数、阻塞对数与 JSON 完全一致；
  5. 同一输入重复运行，结果与 `data.json` 完全一致。

## 6. 样例说明

| 用例 | 规模与构造 | 看点 |
| --- | --- | --- |
| `01-classic.txt` | 3 甲 × 3 乙，完整、无并列 | 只有 1 组稳定解；三人都只拿到第二志愿，提议 6 次 |
| `02-multiple.txt` | 4 甲 × 4 乙，完整、无并列 | 稳定解恰好 2 组且 4 对全不同；期望结果取甲侧主动那一组 |
| `03-incomplete.txt` | 4 甲 × 4 乙，两侧都不完整 | a4 谁都不要、b4 无人可配，两侧各有人落空 |
| `04-ties.txt` | 4 甲 × 4 乙，两侧各 6 组并列 | 打破方向会换结果；「并列不算更偏好」决定了一组解是否稳定 |
| `05-imbalance-a.txt` | 6 甲 × 2 乙，完整 | 甲侧 4 人落空、乙侧无人落空 |
| `06-imbalance-b.txt` | 2 甲 × 5 乙，完整 | 乙侧 3 人落空、甲侧无人落空 |

`samples/expected/<同名>.result.txt` 是逐行期望输出，`<同名>.notes.md` 给出该用例的逐对核验表与结论。`samples/notes.md` 是现场手工配对的记录，只解释来龙去脉，不是口径。
